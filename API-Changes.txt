NEXT MAJOR VERSION - LITE PKI VALIDATION

This release is deliberately source- and binary-incompatible with 2.x. The
behavioral contract and migration rules are in
docs/changes/0003-lite-pki-contract.md.

Planned removals include all proxy-certificate APIs, namespace-policy APIs,
legacy OpenSSL subject hashes, and the detailed copied-reviewer validation
error catalogue. Validator constructors and parameter objects will no longer
accept proxy or namespace settings.

Certificate-array validation treats the first certificate as the target and
the rest as path-building candidates. Successful results contain the resolved
chain and selected trust anchor. Invalid results report one primary native-PKIX
failure with its cause, stage, and certificate position. Error listeners can
observe failures but can no longer suppress them.

OCSP remains supported. Core native OCSP and CRL modes are migrated first;
responder configuration, ordering, nonce, and cache behavior follow in
separately reviewed changes. No OCSP capability is removed silently.

The exact removed and replacement Java symbols will be appended by the PR that
changes each part of the API.

OPENSSL TRUSTSTORE SIMPLIFIED

OpenSSL-style truststores now contain hashed CA certificates and CRLs only.
The library uses the modern OpenSSL subject hash unconditionally. Certificate
collision suffixes remain HASH.0, HASH.1, and so on; CRL suffixes remain
HASH.r0, HASH.r1, and so on. Pre-OpenSSL-1.0 MD5 subject hashes are no longer
recognized. Globus .signing_policy and EUGridPMA .namespaces files are neither
loaded nor enforced.

NATIVE PKIX BASE VALIDATION

When both CRL and OCSP checking are disabled, certificate paths are now built
and validated by the native Bouncy Castle PKIX CertPathBuilder and
CertPathValidator selected explicitly from the BC provider.

For X509Certificate array input, element zero is the target and the remaining
elements are unordered path-building candidates. CertPath input is validated
directly without rebuilding or reordering. An included trust-anchor
certificate is removed before validation, while successful ValidationResult
chains include the selected anchor. An exact configured, self-signed trust
anchor is accepted as a one-certificate input.

Strict CRL-only validation is migrated to native BC in the subsequent native
CRL change. Other revocation configurations remain available on the existing
compatibility path until their dedicated migration changes.


PRIMARY VALIDATION ERROR CONTRACT

ValidationResult is now immutable and contains either no errors for a valid
result or one primary error for an invalid result. getErrors() remains as an
immutable empty or single-element compatibility view. The following public
members were removed:

- ValidationResult(boolean)
- ValidationResult(boolean, List<ValidationError>)
- ValidationResult(boolean, List<ValidationError>, Set<String>,
  List<X509Certificate>)
- ValidationResult.addErrors(List<ValidationError>)
- ValidationResult.setErrors(List<ValidationError>)

Use ValidationResult.valid(List<X509Certificate>),
ValidationResult.invalid(ValidationError), or
ValidationResult.invalid(ValidationError, Set<String>) when constructing a
result. ValidationResult.getPrimaryError() returns the one error directly.

ValidationErrorListener.onValidationError(ValidationError) now returns void.
Listeners receive notification of the immutable primary error but can no
longer suppress it or change the validation verdict.

ValidationStage was added with INPUT, PATH_BUILDING, PATH_VALIDATION, and
REVOCATION values. Native errors expose their stage, original provider message,
original cause, position, and certificate through ValidationError. Stable
native codes and categories use the uppercase names documented in the lite
PKI contract. Provider failures with an unspecified standard reason use
PKIX_FAILURE; provider messages are diagnostic and are not parsed.

CommonX509TrustManager, SSLTrustManager, and
SSLTrustManagerWithHostnameChecking now preserve the primary validation
exception as the cause of their TLS-facing CertificateException.

Revocation configurations not yet migrated continue to use the existing
revocation engine. Their verdicts and OCSP behavior remain available, while
their old detailed error catalogue is temporarily retained until native
revocation replaces that path.


NATIVE STRICT CRL VALIDATION

Validation configured with CrlCheckingMode.REQUIRE and
OCSPCheckingMode.IGNORE now uses the native BC CertPathValidator for strict CRL
checking. The selected path is first validated with revocation disabled and is
then validated against the configured CRL store, so a CRL failure is reported
at the REVOCATION stage rather than as a path-building failure.

The native validator retains all supplied certificate candidates for CRL
issuer discovery and enables native delta-CRL processing. Missing, expired,
malformed, badly signed, and revoking CRLs all fail strict validation. Separate
and indirect CRL signer certificates and delta CRLs remain supported where BC
can resolve them from the supplied certificate and CRL stores.

BC 1.85 reports its CRL failures with an unspecified standard reason, including
definitive revocation. Such failures therefore use PKIX_FAILURE, as required by
the primary-error contract, while preserving REVOCATION stage, certificate
position, provider message, and cause. Provider text is not parsed to infer a
more specific code.

CrlCheckingMode.IF_VALID, every OCSP-enabled configuration, mechanism ordering,
and useAllEnabled continue through the compatibility implementation in this
stacked change. OCSP support is unchanged. The IF_VALID/IF_PRESENT decision and
native OCSP migration remain separate changes.


NATIVE REQUIRED OCSP VALIDATION

Validation configured with CrlCheckingMode.IGNORE and
OCSPCheckingMode.REQUIRE now uses a native BC PKIXRevocationChecker for a
narrow core configuration: exactly one explicit OCSPResponder, no Authority
Information Access extension on any supplied certificate, default responder
settings, and no nonce or persistent cache. Both certificate-array and
asserted-CertPath inputs are supported.

Base path validation and strict OCSP checking are separate passes. The OCSP
pass explicitly adds BC's PKIXRevocationChecker with NO_FALLBACK while leaving
ordinary PKIX revocation disabled, preventing an unintended CRL fallback.
Good responses validate; revoked, unknown, expired, malformed, and badly
signed responses fail.

BC 1.85 exposes no standard reason for the observed OCSP failures, including
definitive revocation, so they use PKIX_FAILURE at the REVOCATION stage while
retaining the provider cause, message, and position where available. Provider
text is not parsed. Malformed response bytes can fail before a certificate
index is assigned and therefore retain position -1.

Configurations using AIA discovery, multiple responders, non-default timeout
or cache controls, nonce, OCSPCheckingMode.IF_AVAILABLE, CRL/OCSP combinations,
mechanism ordering, or useAllEnabled remain on the compatibility path. The
migrated core currently uses BC's native 15-second transport timeout and weak
in-memory response cache; transport controls, caching, and responder discovery
remain separate migration layers.


NATIVE OCSP RESPONDER DISCOVERY

Strict OCSP-only validation now discovers a responder from certificate
Authority Information Access when no explicit OCSPResponder is configured and
every supplied non-anchor certificate contains exactly one HTTP(S) OCSP URI.
Default responder settings are required. Certificate arrays and asserted
CertPath inputs are supported, and configured trust anchors are not themselves
revocation-checked.

The selected path is first validated normally. Each certificate/issuer edge is
then checked in a separate native BC OCSP pass using that certificate's own
discovered responder URI and its already validated issuer. This supports
chains whose CAs advertise different responders without changing the
JVM-global ocsp.enable setting. Failures are remapped to their position in the
complete selected path.

Missing, multiple, malformed, relative, or non-HTTP(S) discovered responder
locations, mixed configured/discovered responders, nonce, non-default cache
controls outside the separately documented memory-cache layer,
OCSPCheckingMode.IF_AVAILABLE, and all CRL/OCSP combinations remain on the
compatibility path. Multiple responders are not retried natively because BC
1.85 does not structurally distinguish responder failures from definitive
revocation; provider messages are not parsed.


NATIVE OCSP CONNECTION TIMEOUT

Strict OCSP-only validation now honors OCSPParametes.getConntectTimeout()
through the native validation path when OCSP response caching is explicitly
disabled with a negative cache TTL. This applies to both the single configured
responder and single-per-certificate AIA configurations migrated previously.
HTTP(S) requests are built and fetched by the retained OCSP transport with the
configured connect/read timeout. The encoded response is then supplied to
PKIXRevocationChecker.setOcspResponses(), and native BC remains responsible
for response signature, signer, certificate status, and freshness validation.

This initial timeout layer applied when caching was disabled. The subsequent
native response-cache layer extends the same per-request transport to default
and custom in-memory cache TTLs. Disk cache, nonce, multiple responders,
responder ordering, OCSPCheckingMode.IF_AVAILABLE, and CRL/OCSP combinations
remain on the compatibility path. Transport and response failures remain
strict invalid results reported as PKIX_FAILURE at the REVOCATION stage;
provider messages are not parsed to infer whether a later responder should be
attempted.


NATIVE OCSP IN-MEMORY RESPONSE CACHE

The previously migrated strict OCSP configurations now use a bounded,
thread-safe, per-validator cache of encoded OCSP responses for every
non-negative OCSPParametes cache TTL. A negative TTL continues to disable
caching, and zero leaves expiry to response metadata. The cache contains at
most 100 certificate/responder entries and expires each response at the
earliest of the configured TTL, HTTP Cache-Control max-age, and OCSP
nextUpdate. Cached byte arrays are copied at both cache boundaries.

Only responses accepted by native BC are added. Every cache hit is supplied
again to PKIXRevocationChecker.setOcspResponses(), so native BC revalidates the
response against the current certificate, issuer, trust, status, and time.
Rejected, forged, malformed, unknown, or revoked responses are not cached.
The cache key includes the responder URI, checked certificate, issuer, and any
explicit trusted responder certificate.

OCSPParametes documents cache TTL in seconds, and the native cache now honors
that unit; the legacy cache accidentally treated the same value as
milliseconds. The default 3600 therefore means one hour, still capped by HTTP
and OCSP response expiry. Persistent disk caching remains on the compatibility
path for its dedicated migration layer. Nonce, multiple/responder ordering,
OCSPCheckingMode.IF_AVAILABLE, and CRL/OCSP combinations remain unchanged on
compatibility code. Persistent caching is added by the following migration
layer.


NATIVE OCSP PERSISTENT RESPONSE CACHE

A configured OCSPParametes disk cache path now extends the native encoded-
response cache across validator instances and process restarts. The native
cache directory is created when necessary. Stable SHA-256 filenames bind each
entry to its responder URI, certificate, issuer, and explicit responder
certificate. Existing serialized ocspresp_ files are ignored; native entries
use a versioned ocspresp-v1-*.cache format with no Java deserialization.

Persistent entries retain their original fetch time and response-expiry limit,
so configured TTL, HTTP max-age, and OCSP nextUpdate are enforced after a
restart. Files have strict headers, lengths, and a 64 KiB bound. Writes use a
same-directory temporary file and atomic replacement when supported.
Malformed, truncated, oversized, future-dated, expired, unreadable, or
otherwise corrupt entries are removed and treated as cache misses. A cache
read or write failure never creates a valid result by itself.

Every loaded response is passed to a fresh PKIXRevocationChecker before use.
If native validation rejects it, the memory and disk entries are deleted and
one response is fetched and checked normally. Only newly fetched responses
accepted by native BC are persisted. A negative cache TTL still disables both
memory and disk caching even when a disk path is configured. Nonce, multiple
responders and ordering, OCSPCheckingMode.IF_AVAILABLE, CRL/OCSP combinations,
and OCSP update notifications remain separate migration layers. Nonce support
is added by the following migration layer.


NATIVE OCSP NONCE VALIDATION

Strict native OCSP validation now honors OCSPParametes.isUseNonce() for both
one configured responder and one discovered responder per certificate. Each
request receives a fresh 16-byte nonce generated by SecureRandom. A response
must contain a BasicOCSPResp nonce extension whose value exactly matches the
request. A missing, malformed, or mismatched nonce fails validation as
PKIX_FAILURE at the REVOCATION stage.

Nonce comparison is a narrow structural check performed before the encoded
response is supplied to PKIXRevocationChecker. Native BC remains responsible
for the response signature, signer authorization, certificate identity and
status, and freshness. Provider messages are not parsed and the compatibility
response verifier is not used as a second validation authority.

Nonce-enabled validation always performs a new request and bypasses both the
memory and persistent response caches, regardless of configured cache TTL or
disk path. A cached response is bound to its original request nonce and can
not establish freshness for a later validation. Nonce-free caching behavior
is unchanged. Multiple responders and ordering, OCSPCheckingMode.IF_AVAILABLE,
CRL/OCSP combinations, and OCSP update notifications remain separate layers.
Deterministic responder selection is added by the following migration layer.


NATIVE OCSP RESPONDER ORDERING

Strict native OCSP validation now accepts multiple configured responders,
multiple certificate AIA responders, and configurations containing both. The
configured responder array and AIA access descriptions each retain their
original order. OCSPParametes.isPreferLocalResponders() selects which group is
placed first; an empty preferred group naturally selects the other group.
The first resulting responder is used independently for each certificate in
the validated path.

Configured responders retain their explicitly trusted responder certificate.
Discovered responders use the already validated issuer context. Timeout,
nonce, and cache behavior from the preceding native layers apply to the
selected responder. A non-empty preferred configured group can be selected
without parsing unused AIA metadata; AIA remains strict whenever the
discovered group is needed.

This layer deliberately selects but does not retry. A native OCSP rejection is
returned immediately and is not converted into success by a later responder.
BC 1.85 does not structurally distinguish revoked, unknown, stale, forged, or
otherwise invalid responses in the observed CertPathValidatorException
reasons, and provider messages are not parsed to guess retryability. Safe
transport-failure fallback remains a separate layer, as do
OCSPCheckingMode.IF_AVAILABLE, CRL/OCSP combinations, and update notifications.

as wildcards may be used.

became more complex
13) added dispose method to validators
14) added new listener to validators: get notification when update error occur
15) added new validator type: FlexibleCertChainValidator
16) optional possibility to add updateError observers in constructor of validators

are returned instead of null if no empty restriction is produced.
18) Changed byte[][] into String[] in case of proxy restrictions (consistently)
19) Added  X500Principal getX500Principal(String rfcDn) to X500NameUtils

smooth addition of OCSP settings in future.
